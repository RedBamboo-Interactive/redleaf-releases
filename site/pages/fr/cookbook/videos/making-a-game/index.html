Transcription

Introduction

Dans l’épisode neuf, on a fait les visuels de lancement d’un jeu appelé Mossbound. Maintenant, on fait le jeu.

Pas une démo vite faite. Une première version jouable, sur des fondations qui tiendront.

En parler d’abord

Un jeu commence par une conversation, pas par du code.

Avant de supposer quoi que ce soit, je demande ce qui compte : pour qui, et quelles sensations il doit donner. Vous répondez.

Ensuite, je propose un pitch et trois piliers, et, tout aussi important, ce que le jeu ne fera pas encore. Vous objectez, et l’idée s’améliore.

Le document de conception

Les décisions vont dans un document de conception : une page dans le projet. Les piliers, les mouvements du chevalier avec des valeurs que vous pouvez ajuster, et une première version jouable assez petite pour être finie.

Chaque modification est dans son historique, pour voir ce qui a été décidé, et pourquoi. Tout le monde travaille à partir de cette page, moi comprise.

Concepts visuels

Puis le style. Explorez large avant de vous engager : trois directions, trois essais chacune.

Le chevalier peint est magnifique, mais il paraît grand et sombre. Le pixel art reste lisible à la taille du jeu. Et celui du livre d’images a un escargot sur son casque.

Alors on repart du chevalier en pixel art, on garde l’escargot, et on le tourne de profil, comme il faut pour un jeu de plateforme. Les images retenues vont dans le projet, sur une page de direction artistique, et chacune garde le prompt et la graine qui l’ont produite.

Le plan

Ensuite, le plan. Je découpe la première version jouable en petites tâches, sur un tableau dans le projet. Chacune a un « terminé quand » clair.

Les sprites définitifs et les finitions attendent dans le backlog : les sensations d’abord, le graphisme ensuite. Quand une tâche démarre, sa carte se déplace, et tout le monde voit où on en est.

Le thème

La musique a droit au même soin. Décrivez l’ambiance, et je fais quelques versions parmi lesquelles choisir.

Vous choisissez celle qui convient. Je l’enregistre dans le projet, et je coupe une boucle propre pour le jeu, pour qu’elle ne claque jamais quand elle se répète.

Les fondations

Maintenant le code, là où les démos rapides prennent souvent des raccourcis. Je crée un nouveau dépôt, et je confie la construction à une session Code, avec un brief tiré du document de conception et du tableau.

Elle pose d’abord les fondations. Une boucle de jeu à pas fixe, pour que les mêmes entrées donnent toujours le même résultat. Les touches associées à des actions. Le chevalier sous forme d’un ensemble clair d’états. Et chaque valeur de jouabilité dans un seul fichier de réglages, pas enfouie dans le code.

Les tests arrivent avec les règles : les états, le temps de grâce au bord des plateformes, les dégâts, les soins.

Dans l’onglet Tests de Code, ils se lancent en un clic.

Première version jouable

Ensuite, il faut que ça marche dans un vrai navigateur. Je lance un test de jeu qui ouvre le jeu, joue la salle du début à la fin, et vérifie le résultat. Les captures d’écran arrivent dans la discussion.

Le voici : la première version jouable.

L’évaluation

Puis je l’évalue au regard des piliers, pas seulement des tests. Le combat est lisible : chaque nuage de spores est annoncé. Le saut est agréable. Mais le petit bond de l’attaque rend les combats flottants.

Vous êtes d’accord, donc il disparaît. Le fichier de réglages change, le document consigne pourquoi, et les cartes terminées passent dans Terminé.

Sous le capot

Alors, qu’est-ce qu’il a fallu ? Une seule discussion, du début à la fin. Le document de conception est une page, et chaque modification est conservée. Les concepts visuels ont tourné sur votre carte graphique, et le plan est un tableau de tâches dans le même projet.

Le thème est venu de la même discussion, et sa boucle est un fichier du projet. Le code vit dans son propre dépôt, construit par une session Code à partir d’un brief écrit, avec des tests pour les règles, et un navigateur qui joue au jeu sur votre machine.

Et c’est une boucle, pas un coup unique : décider, construire, tester, évaluer, et noter ce qui a changé.

Récapitulatif

Donc : parlez d’abord, et notez les décisions. Explorez large, puis planifiez en petites tâches. Construisez les fondations et les tests avant les fonctionnalités, et jouez dans un navigateur après chaque changement.

La prochaine fois : de la première version jouable à la tranche verticale. À bientôt.
