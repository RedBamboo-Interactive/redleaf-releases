Transcript

Opening

In episode nine, we made the launch art for a game called Mossbound. Now we make the game.

Not a one-shot demo. A first playable, on foundations that will hold.

Talk it through

A game starts as a conversation, not as code.

Before I assume anything, I ask what matters: who it's for, and how it should feel. You answer.

Then I propose a pitch and three pillars, and just as important, what the game won't do yet. You push back, and the idea gets better.

The design document

The decisions go into a design document: a page in the project. The pillars, the knight's moves with numbers you can tune, and a first playable small enough to finish.

Every change is in its history, so you can see what was decided, and why. Everyone works from this page, me included.

Concept art

Then the look. Explore wide before you commit: three directions, three takes each.

The painterly knight is beautiful, but it reads tall and grim. Pixel art reads at game size. And the storybook one has a snail on its helmet.

So we iterate from the pixel knight, keep the snail, and turn it side-on, the way a platformer needs. The keepers go into the project, on an art direction page, and every image keeps the prompt and seed that made it.

The plan

Next, the plan. I break the first playable into small tasks, on a board in the project. Each one has a clear "done when".

Final sprites and polish wait in the backlog: feel first, art later. When a task starts, its card moves, and everyone can see where things stand.

The theme

The music gets the same care. Describe the feel, and I make a couple of takes to choose from.

You pick the one that fits. I save it to the project, and cut a clean loop for the game, so it never clicks when it repeats.

Foundations

Now the code, where quick demos usually cut corners. I start a new repository, and hand the build to a Code session, with a brief written from the design document and the board.

It lays the foundations first. A fixed-step game loop, so the same inputs always give the same result. Keys mapped to actions. The knight as a clear set of states. And every feel number in one tuning file, not buried in the code.

Tests come with the rules: states, coyote time, damage, healing.

In Code's Tests tab, they run with one click.

First playable

Then it has to work in a real browser. I run a playtest that opens the game, plays the room from start to finish, and checks the result. The screenshots land in the discussion.

Here it is: the first playable.

Review

Then I review it against the pillars, not just the tests. Combat is readable: every spore cloud is announced. The jump feels good. But the strike's little hop makes fights floaty.

You agree, so it goes. The tuning file changes, the document records why, and the finished cards move to Done.

Under the hood

So what did that take? One discussion, from start to finish. The design document is a page, and every change is kept. The concept art ran on your graphics card, and the plan is a board of tasks in the same project.

The theme came from the same discussion, and its loop is a file in the project. The code lives in its own repository, built by a Code session from a written brief, with tests for the rules, and a browser that plays the game on your machine.

And it's a loop, not a one-shot: decide, build, test, review, and write down what changed.

Recap

So: talk first, and write the decisions down. Explore wide, then plan in small tasks. Build the foundations and the tests before the features, and play it in a browser after every change.
